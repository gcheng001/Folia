## 使用方法

按第一步路由选定的 scene_id，应用下方对应场景的细则组织节点与边。所有场景共用三条硬规则：

1. **主体只画有法律行为的**：出现过但没有签约、付款、持股、举证等行为的主体不进图。
2. **边 label 写「关系类别 + 关键数值」**：如「借款合同 500 万」「持股 60%」「背书转让」「货款支付 120 万」；上游用线型/颜色区分合同流、资金流、标的物流、股权链，Folia 中改用 label 前缀区分，同类关系保持同一措辞。
3. **名义与实际分状态**：上游「名义关系用虚线、实际关系用实线」在 Folia 中翻译为——书面/登记/票面记载的名义关系与实际履行不一致时，己方主张的实际关系用 `confirmed`（有据）或 `inferred`（推定），对方主张或仅有单方陈述的用 `asserted`，双方各执一词的用 `disputed`。

## REL-PARTIES 多主体法律关系

改编自上游：G-02 法律关系图、L-01 签订/履行主体不一致、L-02 多合同关联主体、L-03 债权转让抵债、B-01 票据基本关系、B-06 资金流向、C-01 挂靠、C-04 整体转包、R-04 一地二卖、I-01 信用证、I-05 进出口代理、DR-01 债务结构、DR-08 担保链与追偿、FW-01 家族财产结构。

- 节点：合同主体、付款/收款主体、实际用款人/实际施工人/实际持票人、担保人、关键账户或标的物。核心主体（连线最多者）用 `emphasis: strong` 且排在 nodes 前列。
- 边：先区分「签约关系」和「履行关系」——向第三人付款时，第三人不画成合同主体，用「代收货款」「指令付款」等履行类 label 连接。借款抵债、债权转让、票据还款等特殊履行另成一组边，经还款方与主关系连接。担保链按「主债务 → 担保责任 → 代偿 → 追偿」的路径连边，不画成网状。
- 金额、笔数多时不逐笔画边：合并为一条边并在 label 汇总（「三笔借款共 800 万」），明细留给侧栏或表格。
- 常见失败：只画主体不画行为和法律效果；把代收款第三人画成合同当事人;连线最多的主体放在节点列表末尾导致布局绕行。

## REL-EQUITY 股权与控制结构

改编自上游：S-03 隐名股东、S-06 股权树、S-08 境内外架构、S-11 交叉持股、S-12 实际控制路径、CG-09 公司治理结构。

- 节点：公司、股东（区分名义股东与实际出资人）、持股平台/信托。层级多时自上而下按控制链排列 nodes。
- 边：label 必须带持股比例（「持股 60%」「间接持股 42%」）；工商登记的名义持股用 `confirmed`，隐名代持、实际出资等未登记关系按证据用 `inferred` 或 `asserted`，对抗性主张用 `disputed`。
- 实际控制路径是本图观点时，控制链上的节点用 `emphasis: strong`，间接控制比例写入边 label。
- 交叉持股：被共同持股的公司放 nodes 前列作中心，减少来回连线。
- 常见失败：股东少、结构扁平却硬画成多层树；每次股权变动都画完整结构（应只画最终结构，变动过程交给时间轴场景）；漏掉章程/决议等治理约束对控制权的影响。

## REL-TRANSACTION 交易架构

改编自上游：MA-01 交易架构图、MA-04 交易文件关系图、MA-09 交易前后结构对比、R-06 合作开发权益、C-18 BOT 结构。

- 节点：交易各方、标的公司/标的资产、支付与融资主体。按「主体、标的、对价、控制权」分层组织 nodes 顺序。
- 边：交易文件为边而非节点——SPA、股东协议、担保文件用「签署《…》」类 label 连接义务双方；资金流向与股权交割分别成边（「支付对价 2 亿」「交割 51% 股权」）。已签署生效用 `confirmed`，以交割条件成就为前提的用 `inferred`，尚在谈判或对方口头承诺的用 `asserted` 或 `missing`。
- 合作开发/BOT：按「土地或特许权、资金、项目权益、收益分配」四类关系分别连边，label 前缀保持一致。
- 常见失败：把每份附属文件画成节点导致图变成文件清单；对价、比例不入 label 使架构图失去决策价值；交易前后混在一张图（对比诉求应在 main_view 声明并只画交易后结构，交易前留侧栏）。

## REL-EVIDENCE 证据链与证明关系

改编自上游：G-14 证据链图、S-01 股东资格证据组合、C-06 实际施工人证据、HR-05 竞业限制履行证据。

- 节点：左侧为证据（合同、付款凭证、现场管理记录、聊天记录等，text 写证据名而非全文），右侧为待证事实/争点。待证事实节点用 `emphasis: strong`。
- 边：方向一律「证据 → 待证事实」，label 写证明作用（「证明实际施工」「印证出资合意」）。直接证据用 `confirmed`，间接印证用 `inferred`，对方不认可真实性的用 `disputed`，尚未取得的补强证据用 `missing`（这是 missing 态的主用武之地）。
- 多组证据证明多个事实时按争点分组，同组证据在 nodes 中相邻排列；证明责任在对方的事实，在 label 或节点 text 中注明「由对方举证」。
- 常见失败：把证据内容全文塞进节点；证据与事实之间缺 label 让读者自行脑补证明逻辑；只画己方证据不标证据缺口（缺口正是 missing 边的价值）。

## REL-GENERIC 通用关系图

改编自上游：关系图通用编排套路（playbook「通用图表模式·关系图」）、E-02 共同主体合并、E-03 法律关系分区合并。

- 适用：主体关系为主线但不属于以上业务条线（如侵权多方责任、家事身份关系、行政多方法律关系）。
- 节点：核心主体居前并 `emphasis: strong`；同一阵营的主体在 nodes 中相邻。身份关系与财产/行为关系并存时，先画身份（「父子」「夫妻」），再画行为（「赠与」「代持」），两类 label 措辞分开。
- 边：多种法律关系并存时按关系类别分组连边而不是穿插；有共同主体的多组关系以共同主体为连接点合并，避免同一主体出现两个节点。
- 常见失败：多个法律关系的边混排导致读者无法分辨类别；同一人因出现在两段关系里被画成两个节点；把观点写进节点却不落 main_view。
